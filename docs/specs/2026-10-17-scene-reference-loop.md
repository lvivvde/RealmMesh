# 多实例 Scene 参考业务与首个闭环

- 日期：2026-10-17
- 状态：S1（#161）、S2（#162）、S3 双实例转场恢复（#163）及 S4 动态加入/承载/排空（#164）已实现，S5 尚未实现；本文不构成运行或容量验收记录。
- 路线图：阶段 4；依赖已落地的角色业务（#93）与四层依赖迁移（#152）。
- 决策：[ADR-0015](../adr/0015-scene-confirmed-location-and-binding.md)；术语以 [CONTEXT](../../CONTEXT.md) 为准。

## 范围与交付顺序

客户端保持 Realm 长连接，选角成功后显式进入 Scene；Realm 经独立服务链路转交指令。
首个可玩的增量只有：一个独立 Scene 进程、一个 Scene Shard、两个账号各选一个角色，
进入后能看到对方，任意一方移动后两边都观察到相同的已确认位置。

后续依次增加双实例转场、动态加入与排空、完整故障恢复矩阵。当前不实现 Chat、AOI、
战斗、物理碰撞、客户端预测、地图编辑器、跨机器业务验收或玩法容量压测。
Scene 的内部子状态不增加 Login Stage，也不把 Realm Session 从游戏中退回选角。
现有训练、心跳与登录链语义保持可用；Scene 缺失不能让 Realm 无法启动或阻塞训练。

验收拓扑是一台机器上独立的 Realm 与一至两个 Scene 进程，现有登录四服务按原契约接线。
默认开发拓扑仅在 Scene 实现时扩展；本文不预建目录、注册身份或添加无实现的协议枚举。
本阶段仅要求一个逻辑 Realm 的一个服务进程，不声称解决多个 Realm 进程的账号全局顶替。

## 权威边界

| 对象 | 权威与职责 |
|---|---|
| Realm Session、账号与角色选择 | Realm；客户端不提交可信的账号、角色或承载实例身份 |
| 分片中的合法位置、移动判定、可见成员 | Scene；只发布已由 Realm 确认提交的变更 |
| Scene Binding、Confirmed Location、最后已提交场景指令 | Realm 写入的 MongoDB 场景记录；条件写是生效边界 |
| 发现列表 | etcd Service Registry；仅提供候选，不授予角色归属 |
| 客户端画面 | 已确认状态的观察结果；不能反写为权威位置 |

分片用 `(realm_id, shard_id)` 标识，首版配置分片 1，第二个实例验收时增加分片 2。
承载实例以 `(instance_id, incarnation)` 标识；每次进程启动生成新的不可复用 incarnation，
相同配置 instance_id 的重启也不是原承载者。一个分片在首版配置中只声明一个承载者；
后续动态分配必须用共享的分片归属记录条件更新，不能让两个发现候选各自抢占同一分片。

## 场景记录、提交与幂等

规划新增窄存储接口，复用既有 MongoDB 驱动及隔离夹具；不把场景接口塞进 AccountStore。
每角色一条唯一 `(realm_id, character_id)` 场景记录，至少包含：

| 字段 | 规则 |
|---|---|
| `account_id` | 由 Realm 的已选角色导出，读写均校验归属 |
| `binding_epoch` | 从 1 起单调递增；重绑、离场撤销或转场时推进，耗尽拒绝继续使用 |
| `realm_incarnation`、`session_binding` | 限制提交者，进程重启、会话顶替不能复用旧绑定 |
| `shard_id`、`scene_instance_id`、`scene_incarnation` | 当前承载者；无有效绑定时可以为空，落点单独保留 |
| `confirmed_location` | 上次确认的分片与整数坐标；首次进入才使用出生点 |
| `last_scene_seq`、`last_command_digest`、`last_result` | 最后一次已提交场景指令（客户端或服务端排空转场）及其结果；序号独立于训练 |

读使用 majority，写使用 majority + journal；变更在同一个场景文档内条件提交。
条件包含角色归属、当前绑定版本、会话绑定、承载实例 incarnation 及前一场景序号。
训练仍更新原角色数据，不能整文档替换或让训练写擦掉场景记录。
旧角色没有场景记录时按首次进入处理，唯一索引保证并发初始化只成功一次。

`EnterScene`、`MoveInScene`、`TransferScene` 共用每角色递增的 `scene_seq`：

- `seq == last + 1` 才能产生新的提交；同一角色一次最多一个场景变更在途。
- `seq == last` 且指令类型和业务参数摘要相同，回放已提交结果，不重复移动、转场或激活。
- 同序号不同参数、过旧或跳号均拒绝；不能以新的 `request_id` 绕开幂等。
- 参数错误、已知未提交、满额拒绝不消耗序号。提交响应丢失或写超时时属于结果不确定，
  先回读同一记录；未能确定前不得处理该角色的下一场景变更或回“确定未生效”。
  单次回读仍是旧值不能证明迟到写不会提交；只能继续查询或以同一序号、同一参数做幂等
  条件重试，直到取得该序号的已提交结果，或确认原操作终止且未提交。
- `GetSceneState` 返回当前落点、绑定状态、最后序号与可重放结果；它不产生新的场景指令。
  断线后重新登录、选角并查询，再以同一指令重试或继续；不能把场景序号重置为 1。

会话关闭或被顶替时，Realm 立即停止从该会话派发场景指令并过滤回包，异步按旧绑定条件
撤销归属、通知 Scene 移除角色。已在撤销前提交的落点保留；撤销后的旧结果因版本不符失败。
新会话显式进入时条件取得新绑定，旧清理不得撤销新绑定。Scene 链路失效会回收其可见成员，
进程中断则由新的 Realm incarnation 重新绑定；不能依赖清理消息必达来保证唯一归属。

## 单实例进入、移动与可见性

Realm 在游戏中接受 `EnterScene`：首次使用配置默认分片与出生点；再次进入使用已确认分片
和位置，不允许客户端通过重复进入任意传送。Scene 校验分片可接纳且未排空，准备成员但不广播；
Realm 原子提交新绑定后发送激活确认，收到 Scene 激活与快照后才回进入完成。
提交后激活失败不得宣称未提交，客户端查询/重试，服务端在当前绑定上幂等补发激活。

移动使用二维整数绝对坐标，首版配置有效范围 `0..10000`，出生点 `(0, 0)`，
每步曼哈顿距离不超过 100；不按客户端时钟补算距离，不引入碰撞或速度系统。
Scene 从已确认位置判定请求，产生候选结果；Realm 条件持久写后向 Scene 确认，Scene
应用并广播，Realm 回 `SceneCommandResult`。写失败不应用候选，不广播预测位置。
若写已提交而确认丢失，重试/重建从已提交记录恢复；同一绑定每角色只保留一个候选。

整个分片互相可见，首版每分片至多 16 个角色。加入先取完整快照，之后接有序事件。
Scene 为每次分片运行分配 `shard_incarnation` 和递增 `event_seq`，每个事件包含角色绑定版本；
快照带事件水位，快照与后续事件交接不得漏掉其间加入、移动或离场。
Realm 丢弃旧 incarnation、失效绑定和重复事件，遇到事件缺口主动重新取快照；快照失败则
报告暂不可用，不把缺口后的状态伪装成连续状态。每条快照仍必须小于 Envelope 的 64KiB 上限。
对目标角色推送位置前，其绑定版本必须与 Realm 当前已确认路由一致；旧 Scene 的候选和事件
都不能成为持久写或新的客户端成功回包。中途断线的观察者以新快照恢复，不承诺离线补投。

## 线协议计划

下表编号已在 S1 加入 proto、编解码与权威消息表；S2 已接线进入、移动与查询，S3 已接线转场。
客户端只经 Realm 使用既有 `realmmesh-edge/1` 与 Envelope v1。

| 规划 ID | 消息 | 内容与阶段 |
|---:|---|---|
| 1501 | C2S `EnterScene` | `scene_seq`；游戏中显式进入，不传账号或 Scene 端点 |
| 1502 | S2C `SceneCommandResult` | 指令类型、序号、确认落点、绑定版本、是否回放；用于进入、移动、转场 |
| 1503 | C2S `MoveInScene` | `scene_seq, x, y`；必须已激活且未转场 |
| 1504 | C2S `GetSceneState` | 查询本人权威状态和最后提交结果 |
| 1505 | S2C `SceneState` | 当前绑定阶段、已确认落点、最后序号与结果、可用时的分片快照 |
| 1506 | S2C `SceneEvent` | 加入/位置变更/离场；分片 incarnation、事件序号、角色与绑定版本 |
| 1507 | C2S `TransferScene` | `scene_seq, target_shard_id`；S3 已受理，目标必须在服务端允许列表 |
| 1508 | S2C `SceneUnavailable` | 当前分片暂不可用或需要重新同步，带有限重试建议；保留 Realm Session |

响应回显请求 `request_id`，通知为 0。场景错误使用 1999 `EdgeError`：
`3101` 未进入/正在切换，`3102` 位置或目标参数不合法，`3103` 序号非法或同序号参数不一致，
`3104` 确定未提交且 Scene 暂不可用，`3105` 结果不确定需查询，`3106` 绑定已失效需重新进入。
选角前场景请求沿用 `3003`；资源满额沿用 `429 + retry_after_seconds`；心跳与训练错误不改。
内部故障不得把目标实例地址、凭据或数据库异常回传客户端。

Realm→Scene 首版采用独立 TLS/TCP 监听、长度帧与 Envelope v1，ALPN
`realmmesh-scene/1`，内部消息单独放 `scene_internal/v1`，不接受客户端票据。
内部 1601 `SceneRequest` / 1602 `SceneReply` / 1603 `ScenePush` 已在 S1 定义，覆盖准备、
移动候选、提交确认、激活、状态快照、移除与排空，携带请求关联、绑定版本和双端 incarnation。
操作字段、结果及校验的权威契约见 [协议文档](../protocol.md#realm-与-scene-内部契约)。

链路使用双向 TLS、独立服务 CA 与 Realm/Scene 身份允许列表，校验角色和证书身份；
发现记录、回环地址或知道端口不能替代认证。S2 已补齐通用可选的服务端客户端 CA/身份允许列表、客户端 CA/证书/私钥与服务端 DNS SAN 校验；
旧调用保持原配置默认行为，独立服务 CA 与客户端接入证书分离。
所有内部拨号、读写在专用有界执行器上完成，不能在 Realm 帧线程调用阻塞式客户端流。

## 双实例转场与故障恢复（S3）

角色由分片 A 转向分片 B：

1. Realm 暂停该角色新场景变更，等已派发移动结算；不确定结果先回读，不越过它转场。
2. B 准备目标成员，不可移动、不可广播；A 仍是当前有效归属。目标位置为 B 的配置入口，
   不能由客户端指定；此时失败则释放 B 的准备资源并保持 A。
3. Realm 用 A 的版本、当前会话和上一序号做 CAS，原子写入 B 绑定、新版本、目标落点、
   转场序号与结果。这是唯一切换点；两个 Scene 都不自行变更权威归属。
4. B 激活，A 移除，Realm 切换订阅并下发 B 快照；A 的迟到消息按旧版本丢弃。
   切换提交后 B 不可用时保留 B 的已确认落点并进入恢复，不把 A 重新激活为同一版本。

Realm 在任一步退出、CAS 响应丢失、激活或移除响应丢失，都从权威记录判断切换点前后。
重复准备/激活/移除幂等且有截止；暂存成员在超时或链路失效后回收。禁止用“补偿回滚”覆盖
已经确认的 B 位置。Scene 同名重启必须取得新 incarnation 与新绑定版本，不能复用旧内存事件流。
若原分片承载者失败，在 S4 之前允许重启原承载者恢复；S4 才允许分片重新分配到其他实例。

## 动态加入与排空（S4）

发现到的新实例通过认证且业务就绪后才是新分片或待恢复分片的候选，不自动重平衡已有角色。
分片归属记录 CAS 串行化实例分配，新旧 incarnation 不能同时接纳同一分片的新成员。
排空状态下拒绝新进入和准备，保留存量服务；逐个用 S3 转场迁出成员，目标无容量时保持
draining 并可见地报告未完成，不能先注销发现伪装完成。截止后显式失败，不强行丢弃已确认落点。
无角色后可停用分片并释放其承载归属；有成员的分片不能偷偷改号或映射到不同分片。

停止迁出属于预期可观测行为。一个实例退出只影响其分片，其他实例继续移动；Realm 的独立
链路、队列和截止隔离故障实例，不能用等待故障实例恢复的全局锁阻塞其他场景。

S4 的参考实现保留一个逻辑 Realm、分片 1/2 与两个预授权实例的有界配置。实例允许列表与
逻辑分片入口在 Realm 启动时配置；第二实例可在运行中加入。每实例可承载两片，故障重建
保持原 shard_id；不是自动把角色转往另一个分片。动态模式要求 etcd 必需注册，且不使用静态
端点后备；发现初始化未知不能当成实例消失。业务身份认证及就绪发布成功后才参与承载 CAS。

分片承载记录 `scene_shards` 保存稳定键、owner/incarnation、version 与 draining；实例记录
`scene_instances` 保存本次 incarnation 的接纳状态。分配事务校验并写实例接纳栅栏；实例排空
事务同时关闭接纳并标记全部已承载分片。二者不能交错产生“排空完成后又被分配”的实例。
角色动态条件写在事务内匹配并写承载栅栏，再提交角色记录；新承载生效后旧角色写不可推进。
承载变化/释放才增加分片版本，排空标记不增加，存量移动仍合法。

排空转场由 Realm 在已排发指令结算后串行占用下一 scene_seq，复用 S3 持久提交边界。
成功后通知客户端查询状态，取得新序号与目标快照；与排空竞争的客户端指令若获 3103，先查询
而不是猜测序号。服务端不越过待回读结果。源移除与目标激活未完成时保留排空未完工作；
仅成员数变为零不足以宣称完成。排空尝试标识用于幂等，重复不延长截止，失败后以新标识重试。

## 资源、观测与验证

首版配置上限：每分片 16 人、每角色 1 个场景变更在途、每会话最多 8 个排队场景请求，
每实例最多 64 个内部请求在途；排队等待也计入 3 秒场景指令总截止。Scene 快照只暴露
角色 id 与坐标等必需信息，不含账号凭据。网络、数据工作者和候选队列都有独立有界容量。
单次已提交但尚未广播的结果在重连时以快照恢复；慢客户端出站满额则关闭该会话，不能拖住整分片。

指标至少覆盖进入/移动/转场的结果与延迟、当前绑定数、队列拒绝、旧版本拒绝、待回读结果、
快照重同步和排空进度。标签只用操作与有限结果集，不以账号、角色、request_id 为指标标签；
绑定版本、实例 incarnation 与指令序号可放结构化日志。告警与仪表盘引用同步验证。

每一步都有单测与适当的真实后端集成测试。涉及端口或进程的目标标 `integration`；
场景存储契约使用隔离真实 MongoDB 副本集，禁止共享开发库。验证遵循构建性能约束，
公共头不传播 sol2、驱动头或整个服务类型，不添加服务间 include/链接依赖。

| 交付 | 必须通过的可重复验收 |
|---|---|
| S1：协议与持久边界 | 真实 MongoDB 并发初始化、CAS 竞争、序号重放与参数冲突、写响应不确定后的回读、训练并发不覆盖位置；编解码拒绝坏帧 |
| S2：单实例双人闭环 | 真实登录与选角、独立 Scene；双方初始快照含对方，依次各移动 10 次且双方最终位置与库一致；重复序号不重复事件；非法移动无写；离场可见；Scene 缺失仍能心跳与训练；错误身份连接被拒 |
| S3：双实例转场与恢复 | A→B 成功、准备前后失败、CAS 响应丢失、提交后激活丢失、Realm 重启、Scene 同名重启；旧版本不能推进位置，恢复序号至少覆盖最后成功回包，位置等于数据库最终已提交落点 |
| S4：加入与排空 | 运行中加第二实例承载新分片；并发分配无双承载；带玩家实例排空、无容量时不伪成功；其他分片继续移动 |
| S5：阶段总验收 | 自动化组合故障矩阵、慢消费者与饱和；全量构建测试及三次完整 Scene 验收均通过，且无残留子进程/监听端口 |

S2 起提供验收入口 `scripts/run-scene-acceptance.sh --preset NAME --jobs N`，默认先构建本步
验收目标，不复用与源码不一致的旧二进制；S3/S4 逐步加入分组，最终默认运行所有组。
按既有 `build-dir.sh` 解析构建目录，报告写到 `<构建目录>/acceptance/scene-reference-loop/`。
报告记录 revision、工作树差异摘要、配置哈希、机器与传输能力、逐例结果、数据库核对与原始
日志位置。macOS 与 Linux 各做本机多进程 TLS/TCP 验收；既有 Linux QUIC 门禁继续保留，
不能把本阶段 TLS/TCP 结果写成 Scene 已验证 QUIC、跨机器或玩法容量。

## 任务依赖与实现归属

顺序为 **S1 → S2 → S3 → S4 → S5**，每步独立 PR，完成自身验收后才开始下一步。
父票 [#160](https://github.com/lvivvde/RealmMesh/issues/160) 包含完整规格与 ADR 镜像；
第一步只落协议与可验证的存储原语，不注册空 Scene 服务。

| 顺序 | 实施任务 | 前置 |
|---|---|---|
| S1 | [#161 协议与角色场景持久边界](https://github.com/lvivvde/RealmMesh/issues/161) | 无；已合并 |
| S2 | [#162 独立 Scene 服务与双人移动互见](https://github.com/lvivvde/RealmMesh/issues/162) | S1；已实现 |
| S3 | [#163 双实例转场与归属恢复](https://github.com/lvivvde/RealmMesh/issues/163) | S2 |
| S4 | [#164 动态加入、分片归属与排空](https://github.com/lvivvde/RealmMesh/issues/164) | S3 |
| S5 | [#165 故障矩阵与阶段总验收](https://github.com/lvivvde/RealmMesh/issues/165) | S4 |

- `proto` / `game/common`：消息、窄场景存储与共享编解码，公开头不暴露 Mongo 驱动类型。
- `game/realm`：已选角色入口、指令编排、持久确认与客户端回包；Scene 路由不能进入 Gateway。
- `game/scene`：S2 有实际服务实现时才创建，拥有分片状态、移动判定、可见事件与排空。
- `framework/network`：仅可选的通用 TLS 双向认证能力；不能出现 Scene 消息号或游戏服务身份。
- `apps/mesh_host`：S2 注册 `scene` 的 ServiceModule，并为 Realm 声明可选发现依赖，
  不把 Scene 设为 Realm 启动就绪的硬前提；服务模块之间不直接依赖。
- `game/client`：参考客户端调用与推送消费，复用登录链；不建立第二套登录状态机。

实现 PR 同步 README 实施状态、架构、协议与术语。入口已注册第五个服务 Scene；默认四服务登录拓扑继续可用，
Scene 按需显式加入配置。S2 自动验收运行独立 Scene 与 Realm，见 [运行说明](../operations/scene-reference-loop.md)。
