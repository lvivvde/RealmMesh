# 构建契约夹具的重复配置与发现成本（#119）

本轮承接 PR #147，冻结源码 `216979de85719b445a1d92c0052de503012d87fc`。
用户确认先测量重复配置、测试发现与进程启动成本，只有能证明足够节省空间、
保留全部断言与失败边界时才实施，随后做完整配对。全部测试、严格缓存校验、
真实后端、用例隔离、完整 CTest 串行与原 5% 上限继续保持。

## 结论

**本次没有证据支持靠重复配置或显式 CTest 发现达到 5% 上限，因此不实施跳过
配置、跨例共享夹具或改变发现机制的补丁。** 本轮交付诊断、原始事件、失败与环境
修正记录；产品、测试源码与登记均无改动，没有新的提速百分比或整体通过结论。

P6 的 Mac/Lima 热完整入口中位数为 343.78→395.73、289.41→317.67 秒。
相对旧数值的规划差额为 34.761/13.7895 秒；PR #147 的局部配对收益不能直接扣除
这些差额。现有 649/667 项合集差异仍在，本轮也没有将单例时间相加冒充完整入口。

## 方法和范围

本轮无代码图 MCP，按 Verify 的准确源码回退检查六个构建契约：
`CompilerCacheConfigTest`、`CompilerCacheNativeTest`、
`TestFastScriptTest.FastEntryWatchAndJobsBudget`、
`BuildDirScriptTest.PresetEntriesResolveRecordedBuildDirs`、`BuildGraphTest`、
`DependencyIsolationTest`。不是全库热点或完整调用图的审计。

先运行未修改的真实用例，再用外部 CMake/CTest 包装器记录命令、当前目录、
单调时钟区间与退出码。包装器仍运行同一真实工具，不替换结果；不修改缓存设置。
Native 另用 Python 诊断记录真实 subprocess 与 sleep，不改变它们的实现。
Mac 与 Lima 的测量串行，两个平台不同时取样。

每个诊断阶段仅一次运行，不是五组短场景或三组长场景的性能验收。包装器解释器
启动会增加成本，也会自然老化 Native 输入、减少必要剩余等待；前后顺序与系统
缓存没有组成交替配对，不能把 baseline/profile 墙钟差称为优化收益。
事件内的工具墙钟包含该进程启动及其内部工作，不能进一步拆成纯启动成本。

显式包装事件不覆盖 Native 内部测量 CLI 的 CMake 调用、Ninja 内部重新生成命令，
也不覆盖所有 shell/perl/sysctl 子进程。Native 的独立 Python 诊断另外保留整个
测量 CLI 耗时，避免把这段漏计说成零成本。未测范围不能依据事件缺失声称没有调用。

## 诊断数据

| 显式事件（秒） | Mac | Lima 磁盘重跑 |
| --- | ---: | ---: |
| 全部 CMake 配置（各 93 次） | 8.492 | 2.050 |
| 其中再次请求同一 binaryDir（各 69 次） | 3.886 | 0.794 |
| CTest 显式发现（各 7 次） | 0.049 | 0.032 |
| Native 内部测量 CLI 整段（独立诊断，各 1 次） | 0.951 | 0.215 |


“再次请求同一 binaryDir”按每个套件中命令的 `-B`，或当前目录＋preset 分组，
不代表冗余：其中包含 ON/OFF 切换、flags/生成头变化、目标增删与预期失败。
总配置时间还包括首次配置和编译器检查；即使把这些实际不能全部删掉的工作计入，
本次观测仍不能支持消除规划差额。显式 CTest 发现只有七次，成本更小。

Native 独立诊断中，Mac 安全等待 7.371 秒、20 次真实程序结果验证 3.894 秒；
这些结果验证保留冷/热、关闭、失效、损坏回退与错误传播。Lima 的安全等待为 8.765 秒、20 次程序验证为 0.006 秒。
这两项不是可直接删除的重复准备；也没有证据表明跳过每轮标准配置能保留入口契约。

## 同范围对照的实质限制

P6 R0 为 `4ffb58df9b8d20beec59f4b056d3e9c90859401f`，其
`startup_topology.hpp` 没有当前 `load_topology` 声明，Gateway 的
`gateway_config.hpp` 与 `gateway_event.hpp` 也尚不存在。用实际 R0 头做 C++20
语法检查，当前拓扑装载公共接口调用报 `no member named 'load_topology'`；
Git 对两个新头的精确路径查询也失败。原始头、探针、命令与编译失败在资产中。

所以先前“补齐同测试范围对照”不能理解为把当前全部测试原样放进 R0 就能运行。
新轻量头守卫本来就验证 R0 尚未实施的边界；把新实现一起移回 R0 会改变未优化
基线，省略/改写这些守卫又不再是当前完整合集。若后续确有可行优化，可在当前
完整合集上做优化前后同范围配对；它只能证明该后续改动的效果，不能自动追认
首批 R0 累计验收。原 5% 上限和本追踪的未通过状态保持。

## 失败、环境修正与正确性

- 第一次 Linux 部分源码包漏了 `third_party/sodium/CMakeLists.txt`，Native
  测量 CLI 用例失败；补齐后整组重跑，未挑选旧快样本。
- Linux 的额外 BuildGraph 首次指向旧主检出的图，发现 GTest 链接仍在池内，
  因而失败；改用本聊天先前完整构建、且源码清单一致的独立图后整组重跑。
- 第一次 Linux 全量继承 `/tmp`，该 tmpfs 约 3.9GiB 且余量不足；MongoDB 的
  500MiB 余量检查和 etcd WAL 创建失败。只中断本轮独立构建目录下的 CTest，
  保留日志与退出 130；未清理共享 `/tmp` 或调整服务器要求。
- 环境修正后，Linux 全部诊断和全量正确性统一使用本轮拥有的磁盘 TMPDIR；
  开始前该文件系统约有 24GiB 可用。此前使用 `/tmp` 的 Linux 成功诊断同样
  留作历史，以完整磁盘重跑组作为本轮有效证据。

Mac QUIC 完整 667/667，通过且无跳过，CTest 单次 395.13 秒；Lima 磁盘
重跑同样开启 QUIC，完整 667/667，通过且无跳过，CTest 单次 309.99 秒，
包含配置、稳定 ALL 与串行全量的实际入口墙钟 310.554 秒。

完整运行的构建、测试和配置文件共 416 项 SHA256 与冻结 main 内容逐项一致。
Mac 原检出的 HEAD 与 main 仅有 AGENTS/构建性能文档差异，原目录未提交文档保持。
本次全量是正确性检查：两平台缓存/构建状态不同，不组成性能配对，不将 CTest
时间或单次入口墙钟用作 5% 通过依据。当前无已证明能补足差额的实施候选，因此
没有取成本较高、且不会提供新优化结论的 R0/最终完整性能配对。
