# 构建优化：实施顺序与验收约定

关联[锁定优化实施顺序与三类耗时验收标准](https://github.com/lvivvde/RealmMesh/issues/115)与[构建提速与接口边界优化决策地图](https://github.com/lvivvde/RealmMesh/issues/109)。用户已确认 Q1–Q5 的实施顺序、新冻结起点/分阶段比较、数值目标、采样与未达标收束，并通过 Q6 最终确认完整路线、正式记录与结束首批规划地图。本文不实施优化代码。

## 分阶段路线

| 阶段 | 范围与成果 | 前进条件 |
| --- | --- | --- |
| R0：冻结可比起点 | 独立检出同一源码快照，确认测试和工具状态；登记机器、依赖、能力与测量脚本 | 能构建并取得可信正确性结果；现存失败独立定位，不能挑选通过样本 |
| P1：依赖隔离 | 统一第三方头来源；分别拥有版本/选项并定向隔离通用缓存；明确旧缓存迁移与本机覆盖 | 实际头库匹配；正确生成版本；相同输入配置/构建连续稳定 |
| P2：反馈入口与资源预算 | test-fast、Unit聚合与精确目标选择；watch复用与漏变更修复；--preset/--jobs贯通，仍用Make对照 | 选择、失败、首次启动、增删移与期间变更契约有效；Unit4/完整1验证；预算安全 |
| P3：接口边界 | 配置声明/Lua解析、TrainingRule前置声明、拓扑装载下沉；Gateway轻量事件/启动配置与包含收窄 | 普通消费者不再间接引入sol2；真实绑定能力、生命周期与运行行为保持 |
| P4：Ninja | 外部Make与生成产物依赖接线；独立Ninja/Make预设；所有目录消费者同步迁移 | 双平台新目录构建、删除恢复、完整测试和编译数据库有效后才切默认 |
| P5：ccache与最终复测 | 原生C/CXX缓存AUTO/ON/OFF；本地/CI专用存储、兼容桶及发布规则 | 失效、关闭、缺失、损坏和CI净成本验收；同范围最终比较通过 |

范围以已确认的[隔离](dependency-isolation-decisions.md)、[入口](build-test-entry-decisions.md)、[接口](interface-boundaries-proposal.md)和[工具/缓存](build-tool-cache-decisions.md)决策为准。首批不增加全面PIMPL、存储虚接口、PCH/Unity、下载包层、预编译依赖包或共享缓存服务。libsodium仍用独立Make串行，首批未额外接缓存。

R0在任何优化前建立。已有测试缺陷如需修复，先独立完成并冻结修复后的起点；不把测试修复产生的时间变化计入优化。默认环境如无法构建，允许已记录的正确来源覆盖作为测量适配，在前后双方保持一致；不得把失败默认配置当作“之前耗时”。P1修复的真实状态污染另外报告，不用后续缓存掩盖。

R0按当前仓库未优化默认路径使用Make串行、cache OFF，清除测量中无意继承的并行环境并明确记录。若实施开始时仓库默认已变化，先重新核实并冻结实际起点，不人为撤掉已有优化来扩大收益。

每个阶段应可单独审阅和回退；不要求每阶段只有一个提交，但不可把运行时边界变化与生成器/缓存变化混成无法归因的大提交。每阶段保存父版本、阶段版本与报告；最终再对R0比较累计效果。业务代码或测试合集变化产生新比较组，不拼接旧秒数。

## 场景、指标与已选择目标

Q3已选择下表作为首批性能目标，两平台分别满足，不互相抵消；全部数值是工程目标，未实测达到。

| 场景 | 比较与指标 | 目标 |
| --- | --- | --- |
| 已备齐固定源码的全量构建 | 产物为空，cache OFF；R0原并行设置与最终资源预算分别明确登记，完整ALL范围相同 | build中位墙钟下降至少20% |
| 默认Unit，无改动 | 每次标准配置＋构建所需目标＋全部Unit；与R0的配置＋ALL构建＋同一Unit集合串行反馈比较 | 连续入口中位总耗时下降至少30% |
| 默认Unit，代表.cpp真实改动 | 同样的编辑补丁/测试集合；配置、构建、测试合计，实际工作量另列 | 连续入口中位总耗时下降至少30% |
| Lua重头内部变化 | cache OFF、同jobs；前后相同内部变化，build计时，另列编译源码与链接消费者 | build中位耗时下降至少30%；仅使用配置结果的消费者零编译 |
| 兼容缓存的全量重建 | 同阶段同jobs/工具链/路径、相同待构建状态，cache OFF与已预热兼容cache比较 | 净构建等待下降至少20%；CI包含缓存恢复/保存成本 |
| 热完整验证 | 标准配置＋稳定无操作ALL构建＋完整CTest，测试并行1，前后同一测试全集与能力 | 正确性全通过；中位总耗时回退不超过5% |

全量构建目标允许计入已选择的并行收益，但生成器归因必须另做Make/Ninja同jobs、cache OFF对照；不能全部归功于Ninja。接口阶段同jobs对照；最终实际开发配置另报。两项默认Unit目标的主比较也使用cache OFF，允许计入目标选择与已确认测试并行；AUTO/ON下的实际开发反馈另报，不能通过预先缓存编辑变体达到主目标，也不得将Unit反馈称为完整验证提速。

同时记录完整冷入口（首次来源准备＋配置＋全量构建＋完整CTest）与热完整入口。冷完整入口的构建收益应体现于阶段数据，来源准备和测试段各保留不回退检查；默认不要求与热完整入口相同的整体提速百分比。未预置来源、网络变化和新runner的一次数据不能作为确定的回退或收益，须另分比较组。首次真正无来源/无产物/无编译缓存作为独立场景报告，不冒充已备源码冷构建。

对既有稳定公共接口的真实变化，消费者应正常重编译，不以“所有公共头都零传播”为目标。Lua基线33次编译/53次链接仅是旧代表样本；本轮不把33当所有新快照的固定基数，也不要求接口拆分消除静态链接传播。

## 正确性与资源硬门槛

- 两平台完整构建、当前全部CTest与必要接入验收通过；Linux QUIC必须开启，并保留既有M1–M4门槛。macOS本机记录有/无QUIC，CI仍TLS/TCP；实际未测的架构/能力组合明确标注。Linux Lima用于本地性能配对，Linux x86_64 CI负责既有生产回归；不同runner数字不混合。
- 正常无修改的配置/构建连续至少三轮：依赖版本头内容与mtime稳定，无非预期编译或链接。P1也检查首次重新配置，不允许先额外重编译一次再只提交后来稳定样本。R0已知污染保留报告，稳定性能对照不利用它放大收益。
- 普通配置/业务头独立编译并检查真实依赖；Lua内部变化不触发只用配置结果的消费者。Lua泛型绑定、沙箱、线程归属、失败热更保留旧模块、TrainingRule与Gateway回收顺序等既有行为保持。
- Ninja生成依赖与删除单个产物恢复无竞态；protobuf生成源码/头、libsodium安装库/头均验证，不靠删除整个build规避。Make回退、cache OFF、本机派生preset、启动与验收目录一致。
- 默认预算当前Mac8/Linux2/CI2，Ninja链接1、外部Make1；记录整个测量进程树与平台整体压力，不能用单次ru_maxrss乘jobs宣布通过。不得OOM、因磁盘耗尽失败或新增持续swap抖动。Linux测量期间可用内存保留至少1GiB，按VM/容器实际限额核实，不能只读无限额宿主MemAvailable；macOS保持正常内存压力，无新增持续换页。达不到则降低预算并重测，不自动扩大VM或依赖swap换取速度。
- Linux构建和fixture采用独立磁盘目录，避免历史tmpfs容量污染；前后使用相同存储。开测前按实际源码/双对照build、fixture峰值、日志和专用cache上限确认空间并留余量，不把某个临时机器路径写成仓库默认。只清理由测量创建并明确拥有的目录/进程。
- 测试不跳过、删除或降低覆盖/工作量来达标；跳过须逐项报告，允许项按原平台政策核实，不能泛称全绿。自动化只用隔离etcd/MongoDB，不接共享开发库。

单个平台硬门槛失败就是该阶段未通过。测试不稳定或环境失败独立保存，修复/换环境后完整重测相关比较组；不把失败样本算成功耗时，也不悄悄从证据中删掉。

## 采样与可复现协议

Q4已选择短场景至少5组前后配对，R0/最终的冷构建和完整验证各至少3组。兼容缓存净重建按长场景至少3组。中间阶段先在两平台完成完整正确性运行，时间仅作筛查；需要断言阶段收益或疑似回退时补足配对样本，不用一次命中确认上线。

1. 冻结提交＋任何补丁SHA、测量脚本SHA；同机器、工具链、SDK、依赖版本/补丁、flags与能力配对。机器/VM配置不变，同宿主Mac与Linux避免同时测量。先准备fixture工具，不在计时中混入其首次安装。
2. 每组交替前后顺序，记录宿主负载与异常；缓存状态、源码准备和测试范围明示。短场景先做一次双方预热，不纳入正式样本；真正冷/首次获取场景不通过预热偷留产物。OS页缓存不强制清空，准确称“产物冷/编译缓存冷”。
3. 全量cache OFF前后均无编译产物，固定来源也包含外部sodium源码已准备的条件。测量辅助可提前完成download步并登记原包/源码/补丁校验，不改变生产来源政策；首次网络获取另计。无法保证同样来源准备状态的样本另列，不能将其混入20%门槛。
4. 兼容cache重建保持同阶段稳定路径；预热必须来自完全相同工具链/flags/生成输入。重新建立空产物状态，包括外部库，不能偷偷复用未缓存的libsodium已编译产物。关闭/开启双方的下载与配置准备一致。完整传输成本包括restore、save、缓存检查；初次填充和首次上传另外报告，不能只取restore最快的一次。
5. 无改动、cpp、私有头、Lua重头、普通稳定接口头、proto等分别重放可版本化补丁。旧注释探针继续用于历史对照；主编辑指标增加改变预处理token、保持测试行为的等价实现/内部布局变体，避免ccache预处理命中只说明注释被忽略。每次恢复源码原始字节并恢复稳定状态，保存原/变体hash。
6. 主计时包含每次标准配置与实际入口执行，不由独立阶段中位数相加冒充总时间。分列configure/download/preparation、build、test与总墙钟；并行编译时间相加不能替代总墙钟。
7. 主计时关闭额外debug追踪，前后使用相同轻量观测方式。另做工作量诊断，保存真实编译/链接、归档/外部构建及测试发现阶段证据；区分launcher调用、实际compiler执行、cache hit/miss/不可缓存。ccache统计结合实际诊断核对，compile_commands条目数不作为实际执行计数。最低CMake3.20功能验证不依赖它不支持的新版观测属性。
8. 原始每次结果、退出码、样本数、median/min/max、配对差值和异常原因全部保留。主下降率为1−median(after)/median(before)，至少多数配对方向一致；同时检查实际工作量解释。极差或负载足以掩盖差异时补测，不能凭单个最快结果达标。
9. 初组无法判定时先修复污染，再补一批；短场景最多扩展到9组、长场景5组，仍不清晰记“无法判定/未通过”，重新安排受控环境或决策，不无期限重复。离群/失败不从原始资产删除；排除须附事先可解释的环境原因和完整替代样本。

[ccache预处理模式](https://ccache.dev/manual/latest.html#_the_preprocessor_mode)按预处理结果计算键，因此仅注释变化可能命中旧结果；这支持区分探针，不能据此断言本项目已取得缓存收益。

## 阶段交付与未达标处理

Q5已选择正确性、覆盖、生成文件恢复和资源安全优先作为硬门槛；性能未达标先按阶段数据定位，在已确认范围内调低/调整jobs、修正依赖表达、缓存配置或入口工作量。没有净收益的Ninja/缓存采用明确Make/OFF回退，保留报告；不得把回退后的状态称为目标方案验收完成。

仍未达标时记录未通过并重新进行有界决策，不因百分比要求直接扩大到全面PIMPL、PCH/Unity或新依赖体系。诊断可继续收集源码证据；新增影响运行行为/接口/测试发现机制的设计变更，先形成明确问题与范围供人决定。发现全新热点不能替代已选择场景，从而回避原目标。

每阶段随实现更新入口帮助、tests/README、预设/本机覆盖说明与CI配置。改变已实现结构、协议或领域词的阶段，按AGENTS在同PR同步docs/architecture、docs/protocol、CONTEXT与README实施状态；CONTEXT仅写领域词义，不混入构建或实施细节。本计划要求保持领域与wire行为；文档准确反映实际变化，不为拆头发明术语。遵守相关ADR；发现矛盾明确提请重审，不悄悄更改平台、依赖或测试政策。

阶段报告至少包含版本/补丁、环境、preset/binaryDir、工具/能力、并行/缓存/来源状态、测试身份、原始样本、工作量、资源峰值/压力、结果、限制与回退命令。量化最终达标和行为通过都完成后，才宣布首批优化验收完成；规划地图关闭仅表示路线清晰。

## 地图收束与后续分支

首批方案完成后可能需要更深Lua核心、Gateway布局、存储视图、其他高传播头或下载层/PCH/Unity等；这些不是首批实施前仍缺失的设计。用户已确认将当前地图的模糊项收束为本节的测量后触发政策：只有新数据明确成本、消费者与可行边界时，创建具体后续决策；不能在没有证据时先安排全面重构。

若首批全部门槛通过，交付首批结果与未采用项理由；若未通过，按未达标政策形成明确问题，再选择有界后续。当前地图完成的是首批路线及验收定义，不意味着代码已优化、未来不再有决策，或未知热点已被消除。用户已最终确认按此结束本地图。
