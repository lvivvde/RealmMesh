# 网关定位为登录管线,业务流量由客户端直连业务服

---
status: accepted
---

百万洪峰改造重排了接入时序:旧链路 Login → Realm 选角 → Gateway 入场,改为 健全服 → 排队 → 网关(验票+限流拉取账号数据)→ 直连业务服。网关只负责登录与鉴权:Edge Session 三阶段 `pending → fetching → handed-off`,拉取完成后向客户端下发业务服 IP + EnterRealm 票据,客户端直连业务服,网关不中转业务流量。这样砍掉一跳常驻中转,网关从"长连接的家"变成"登录管线"(瞬时洪峰承载、稳态零负载),`established` 终态语义随之退役;旧 Login 服由健全服取代,EnterGame 票据用途更名 EnterRealm(签发点从 Realm 移到网关、兑换点仍在业务侧)。

## Considered Options

- **网关桥接业务(保留中转)**:被否。多一跳常驻转发,网关要为稳态游戏流量持续付出连接与带宽,且与"网关只管登录鉴权"的容量模型冲突。
- **保留旧时序(Login/Realm 在网关之前)**:被否。无法在业务入口前实施"限流拉取后才放行"的准入控制。

## Consequences

- 洪峰末约 100 万长连接的落点在业务服侧,业务服 `conn_free` 与网关管线额度双源并入放行阀门。
- 网关 IO 分片(共享无关多分片)按登录管线瞬时承载设计(10 万连接/实例),不按稳态业务连接设计。
- 内部服务桥接认证强度(mTLS vs 内网+etcd 校验)为显式 TODO。
